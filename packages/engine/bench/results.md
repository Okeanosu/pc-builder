# Engine benchmark

Generated by `pnpm --filter @pc/engine bench` (`bench/run.ts`). Synthetic catalogs from a seeded PRNG
(`syntheticCatalog(size, 7)`, category mix of the seed data, ~10% out of stock); the size column shows
total (in-stock) products. Workload per catalog: office 20M, gaming 25M, graphics 40M, ai 60M.
Each scenario is run once for warm-up, then 25× for `full` and 3× for the exhaustive
strategies; times are wall-clock per `solve()` call (domain building + search + label selection + build output).
Node limit: 2,000,000 search nodes per call.

- Machine: Apple M3 · Node v22.20.0 · 2026-11-07
- full p95 on the 250-product catalog: **11.5 ms** (target < 300 ms) → PASS
- † = at least one run hit the node limit (`stats.capped`): the strategy stopped early, so its time is bounded by
  the cap and its builds may be sub-optimal. "optimal" counts runs whose best build has the same score as `full`.
- `full` is the reference of that column, so its rows say "reference" rather than a self-comparison of 100/100.
  The evidence that `full` is optimal is the equivalence check `pnpm --filter @pc/engine bench:equivalence`: on
  random catalogs small enough for exhaustive forward checking to finish, `full` returned exactly the same labelled
  builds, scores, totals and infeasibility diagnoses in **1,080 cases** (48 products, 30 seeds; default arguments)
  and **432 cases** (`bench:equivalence 72 12`), **0 mismatches**, 0 label-contract violations, 0 cases skipped
  as capped (re-run 2026-11-08). From 100 products up the exhaustive strategies hit the node limit, so there is no
  independent reference at those sizes.
- Note: this file is generated by `bench/run.ts`; the "reference" cells and this note were edited by hand after the
  run, so a regenerated file prints the old self-comparison until run.ts is changed.
